### Feature CRITICO-001 — Bloquear auto-atualização de colunas sensíveis em `usuarios` e separar políticas de self-update/admin

- **ID:** CRITICO-001
- **Severidade efetiva:** CRITICO
- **Arquivos afetados:**
  - `supabase/migrations/20260701000000_core_users_auth_and_security.sql`
  - `supabase/migrations/20260707000000_security_fixes_rls_and_storage.sql`
  - Nova migration de remediação

**Problema**
A política `Admins can update all users` permite que qualquer usuário autenticado atualize a própria linha (`auth.uid() = id`) sem restrição de colunas e sem `WITH CHECK`. Um usuário pode executar `UPDATE usuarios SET tipo='admin' WHERE id=auth.uid()`, passando a ser reconhecido por `is_admin()` e acessando dados de todos os tenants. Também permite alterar `trial_ends_at` e `is_blocked`.

**Critérios de Aceite**
- [ ] `authenticated` NÃO pode executar `UPDATE` nas colunas `tipo`, `is_blocked`, `trial_ends_at`, `commission_rate`, `referral_code`, `referred_by_code` da própria linha nem de terceiros.
- [ ] Self-update permitido somente para campos de perfil (`nome_completo`, `telefone`, `logo_url` e demais campos não sensíveis), com `WITH CHECK (auth.uid() = id)`.
- [ ] Atualização de terceiros permitida somente a admins, via política separada com `USING (public.is_admin(auth.uid()))` e `WITH CHECK (public.is_admin(auth.uid()))`.
- [ ] Um trigger impede não-admins de alterar `tipo` mesmo que tentem por outro caminho.

**Passos de Implementação**
1. Criar migration nova que execute `REVOKE UPDATE (tipo, is_blocked, trial_ends_at, commission_rate, referral_code, referred_by_code) ON public.usuarios FROM authenticated;`.
2. Remover (`DROP POLICY`) as políticas duplicadas de UPDATE e recriar duas políticas separadas:
   - `"Users can update own profile"`: `FOR UPDATE TO authenticated USING (auth.uid() = id) WITH CHECK (auth.uid() = id)` — garantindo que as colunas revogadas não possam ser escritas.
   - `"Admins can update all users"`: `FOR UPDATE TO authenticated USING (public.is_admin(auth.uid())) WITH CHECK (public.is_admin(auth.uid()))`.
3. Criar trigger `before_update_usuarios_block_tipo` que, quando `OLD.tipo IS DISTINCT FROM NEW.tipo` e o usuário corrente não for admin (`NOT public.is_admin(auth.uid())`), levanta exceção.
4. Ajustar a função `is_admin()` se necessário para refletir a leitura de `tipo` pós-correção.

**Verificação**
- Como usuário não-admin autenticado, tentar `UPDATE usuarios SET tipo='admin' WHERE id=auth.uid()` e confirmar erro de permissão (RLS) ou de trigger.
- Confirmar que atualizar `nome_completo` do próprio usuário continua funcionando.
- Confirmar que admin consegue atualizar dados de terceiros.

### Feature CRITICO-002 — Tornar obrigatória a autenticação no endpoint `create-checkout`

- **ID:** CRITICO-002
- **Severidade efetiva:** CRITICO
- **Arquivos afetados:**
  - `supabase/functions/create-checkout/index.ts`
  - `src/lib/planos/actions.ts` (chamador — ver MEDIO-003)

**Problema**
A Edge Function trata autenticação como opcional e ignora o JWT quando o token é a anon key. Sem usuário autenticado, a verificação de IDOR (`company_id` vs. usuário) é pulada e a função usa a service role key para `upsert` em `company`/`customers` e criar sessões Stripe para qualquer `company_id`/`price_id`.

**Critérios de Aceite**
- [ ] `create-checkout` retorna `401` quando o header `Authorization` está ausente, inválido ou é a anon key.
- [ ] O endpoint exige um JWT de usuário válido (via `supabase.auth.getUser(token)`), nunca aceitando anon key como identidade.
- [ ] A verificação de propriedade (`company_id` pertence ao usuário via `user_company` ou é admin) é executada **sempre**, antes de qualquer escrita.
- [ ] A service role key só é usada **após** a autenticação estrita e a autorização do usuário.
- [ ] Respostas de erro padronizadas (401/403) sem vazamento de detalhes internos.

**Passos de Implementação**
1. Reescrever o bloco de autenticação para extrair o token do header e rejeitar imediatamente se ausente ou igual a `SUPABASE_ANON_KEY`.
2. Chamar `supabase.auth.getUser(token)` e retornar `401` se não houver usuário válido.
3. Mover a validação de `company_id` para dentro do fluxo autenticado, antes de qualquer `upsert` ou chamada ao Stripe.
4. Garantir que o client da service role seja usado somente após a confirmação de propriedade/admin.
5. Ajustar o chamador `createCheckoutSessionAction` para enviar o token de sessão do usuário (ver MEDIO-003).

**Verificação**
- Chamar o endpoint sem token → `401`.
- Chamar com anon key → `401`.
- Chamar com token de usuário que não é dono do `company_id` → `403`.
- Chamar com token do dono → sucesso na criação da sessão.

### Feature CRITICO-004 — Remover auto-declaração de `tipo=parceiro` no cadastro

- **ID:** CRITICO-004
- **Severidade efetiva:** CRITICO
- **Arquivos afetados:**
  - `src/lib/auth/actions.ts` (`signUpAction`, `getClientLayoutDataAction`)
  - `supabase/migrations/20260706000000_cleanup_and_referral_fix.sql` (`handle_new_user`)
  - Nova action/edge function administrativa para elevação a parceiro

**Problema**
O `tipo` do usuário é definido a partir de `user_metadata` controlado pelo cliente no `signUp`. Qualquer pessoa registra `tipo: "parceiro"` (e `commission_rate` arbitrário), o trigger `handle_new_user` grava `tipo='parceiro'`/`commission_rate=25`, e `getClientLayoutDataAction` libera acesso sem trial/assinatura.

**Critérios de Aceite**
- [ ] `signUpAction` não aceita `tipo` nem `commission_rate` do cliente (removidos do `optionsData`).
- [ ] Todos os novos usuários são criados como `tipo='comum'` no servidor.
- [ ] `handle_new_user` não lê `tipo`/`commission_rate` de `raw_user_meta_data`; define valores padrão seguros (`comum`, `commission_rate` padrão).
- [ ] Elevação a `parceiro` só ocorre por fluxo administrativo autenticado (action protegida por `is_admin` ou edge function com service role).
- [ ] `getClientLayoutDataAction` continua tratando parceiro sem trial apenas quando o `tipo` for validamente `parceiro` no banco (não via metadata).

**Passos de Implementação**
1. Remover `tipo` e `commission_rate` do tipo/payload aceito em `signUpAction`; passar `options.data` apenas com campos de perfil.
2. Reescrever `handle_new_user` para forçar `tipo='comum'` e `commission_rate` padrão (10.0, `commission_model` padrão) ignorando metadata.
3. Criar action/edge function administrativa (protegida por `requireAdminAccess()`) para atualizar `tipo`/`commission_rate`/`commission_model` de um usuário específico.
4. Garantir que `getClientLayoutDataAction` derive o `tipo` exclusivamente da tabela `usuarios` (não de metadata).
5. Auditar `register/parceiros` para não enviar `tipo` ao signup (o formulário pode existir, mas não pode auto-elevar privilégio).

**Verificação**
- Registrar conta com payload forjado contendo `tipo:'parceiro'` e confirmar que o usuário é criado como `comum`.
- Confirmar que `getClientLayoutDataAction` retorna `trialExpired` conforme o paywall para a conta `comum`.
- Confirmar que a ação administrativa eleva a `parceiro` com sucesso apenas para admins.
