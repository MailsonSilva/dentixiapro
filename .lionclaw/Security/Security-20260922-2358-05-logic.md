### LOGIC-001: Escalação de privilégio — qualquer usuário pode se auto-declarar "parceiro" no cadastro e burlar o paywall
- **Severidade:** CRITICO
- **Arquivo(s):** `src/lib/auth/actions.ts` (signUpAction), `supabase/migrations/20260706000000_cleanup_and_referral_fix.sql` (handle_new_user), `src/lib/auth/actions.ts` (getClientLayoutDataAction)
- **Trecho:**

  ```typescript
  }) {
    const { data, error } = await supabase.auth.signUp({

  ```

Remover esses campos do `optionsData` aceito no signup, forçar `tipo='comum'` no servidor (ou validar contra um allowlist/serviço administrativo) e criar a elevação a "parceiro" somente por fluxo administrativo autenticado (ex.: ação protegida por `is_admin` ou edge function com service role).

### LOGIC-002: IDOR — `getProfileCompanyAction` retorna `company_id` de qualquer usuário sem validar autenticação
- **Severidade:** ALTO
- **Arquivo(s):** `src/lib/perfil/actions.ts:27`
- **Trecho:**

### LOGIC-007: `getTargetAudienceCountAction` para "inactive" usa `.or()` encadeado e perde o filtro de bloqueados
- **Severidade:** MEDIO
- **Arquivo(s):** `src/lib/admin/actions.ts` (getTargetAudienceCountAction)
- **Trecho:**
  ```typescript

    const { count } = await supabase
      .from("usuarios")
      .select("id", { count: "exact", head: true })
      .or("is_blocked.is.null,is_blocked.eq.false")
      .or(`trial_ends_at.lt.${now.toISOString()},trial_ends_at.is.null`);
    return { count: count || 0, error: null };
  ```

- **Impacto:** No Supabase/PostgREST, chamadas subsequentes a `.or()` substituem a condição `OR` anterior, em vez de compor. - **Recomendacao:** Combinar as condições em uma única chamada `.or(...)` ou usar filtros encadeados separados (ex.: `.or("is_blocked.is.null,is_blocked.eq.false").or(...)` não funciona; usar `.not("is_blocked","is",true)` + `.or("trial_ends_at.lt...,trial_ends_at.is.null")`). Testar a contagem resultante contra dados de controle.
