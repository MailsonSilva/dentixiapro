### AUTH-001: Escalação de privilégio via política RLS de UPDATE em `public.usuarios`
- **Severidade:** CRITICO
- **Arquivo(s):** supabase/migrations/20260701000000_core_users_auth_and_security.sql:41-46; supabase/migrations/20260707000000_security_fixes_rls_and_storage.sql:30-35
- **Trecho:**
  ```sql
  CREATE POLICY "Admins can update all users" 
  ON public.usuarios FOR UPDATE 
  TO authenticated 
  USING (
    auth.uid() = id OR public.is_admin(auth.uid())
  );
  ```
- **Impacto:** A política permite que qualquer usuário autenticado atualize a própria linha (`auth.uid() = id`) sem restrição de colunas e sem `WITH CHECK` específico. Como a tabela `usuarios` contém as colunas `tipo`, `is_blocked` e `trial_ends_at`, um usuário comum pode usar o cliente Supabase diretamente (a anon key é pública via `NEXT_PUBLIC_SUPABASE_ANON_KEY`) e executar `update({ tipo: 'admin' })` na própria linha, tornando-se administrador do sistema. Também pode estender o próprio trial e remover bloqueios.
- **Recomendacao:** Separar as políticas: criar uma política de UPDATE para o próprio usuário restrita a colunas não sensíveis (via RPC/trigger de allowlist, já que RLS não limita colunas) e uma política exclusiva de admin para `tipo`, `is_blocked`, `trial_ends_at` e demais campos sensíveis. Na prática, remover o UPDATE direto de `usuarios` para usuários comuns e expor apenas funções `SECURITY DEFINER`/RPCs com validação de campos permitidos.

### AUTH-002: Autenticação opcional no endpoint `create-checkout` permite criação de sessão Stripe e escrita no banco sem login
- **Severidade:** CRITICO
- **Arquivo(s):** supabase/functions/create-checkout/index.ts:33-42; supabase/functions/create-checkout/index.ts:101-150
- **Trecho:**
  ```ts
  // Validação opcional de JWT se fornecido no cabeçalho
  const authHeader = req.headers.get("Authorization");
  let authenticatedUser: any = null;
  if (authHeader && authHeader.startsWith("Bearer ")) {
    const token = authHeader.replace("Bearer ", "").trim();
    if (token && token !== Deno.env.get("SUPABASE_ANON_KEY")) {
      const { data: { user } } = await supabase.auth.getUser(token);
      authenticatedUser = user;
    }
  }
  ```
- **Impacto:** A autenticação é tratada como opcional e é explicitamente ignorada quando o token enviado é a anon key — exatamente o que o frontend faz em `src/lib/planos/actions.ts` (`Authorization: Bearer ${anonKey}`). Sem usuário autenticado, todo o bloco de verificação de IDOR (`company_id` vs. usuário) é pulado, e a função segue usando a **service role key** para fazer `upsert` em `company` e `customers` e criar sessões de checkout do Stripe para qualquer `company_id`/`price_id` fornecidos. Um atacante não autenticado (e sem CORS restrito) pode manipular dados de faturamento, criar sessões de pagamento fraudulentas e potencialmente sequestrar o vínculo `customers.stripe_customer_id` de uma empresa.
- **Recomendacao:** Tornar a autenticação obrigatória: exigir um JWT de usuário válido (nunca aceitar anon key como credencial de identidade), retornar 401 se ausente/inválido e sempre executar a verificação de propriedade/`user_company`/admin antes de qualquer escrita. Além disso, nunca usar a service role key em endpoints acessíveis publicamente sem autenticação estrita.

### AUTH-003: Bucket `simulacoes` permanece público, expondo imagens de pacientes sem autenticação
- **Severidade:** CRITICO
- **Arquivo(s):** supabase/migrations/20260702000000_storage_buckets_and_rls.sql:5-9; supabase/migrations/20260707000000_security_fixes_rls_and_storage.sql:43-52
- **Trecho:**
  ```sql
  INSERT INTO storage.buckets (id, name, public)
  VALUES 
    ('dentixia', 'dentixia', true),
    ('simulacoes', 'simulacoes', true),
    ('logoEmpresa', 'logoEmpresa', true)
  ON CONFLICT (id) DO NOTHING;
  ```
- **Impacto:** A migração `20260707000000` remove a política pública de leitura de `storage.objects` e cria uma política restrita, mas **não altera a flag `public = true` do bucket `simulacoes`**. Em buckets públicos, o endpoint público do Supabase Storage serve os objetos sem autenticação, independentemente das políticas RLS. Imagens de simulações odontológicas de pacientes (dados sensíveis de saúde/LGPD) permanecem acessíveis por URL pública.
- **Recomendacao:** Executar `UPDATE storage.buckets SET public = false WHERE id = 'simulacoes';` e passar a servir as imagens via URLs assinadas (`createSignedUrl`) ou proxy autenticado com verificação de propriedade no servidor.

### AUTH-004: IDOR em `getProfileCompanyAction` expõe `company_id` de qualquer usuário
- **Severidade:** MEDIO
- **Arquivo(s):** src/lib/perfil/actions.ts:21-39
- **Trecho:**
  ```ts
  export async function getProfileCompanyAction(userId: string) {
    const admin = getSupabaseAdmin();
    if (!admin) return userId;

    const { data: ucData } = await admin
      .from("user_company")
      .select("company_id")
      .eq("user_id", userId)
      .maybeSingle();

    if (ucData?.company_id) return ucData.company_id;
    ...
  }
  ```
- **Impacto:** A server action não autentica nem autoriza o chamador e ainda usa a service role key (que ignora RLS). Qualquer pessoa que consiga invocar a action pode passar um `userId` arbitrário e obter o `company_id` correspondente, expondo identificadores internos usados no faturamento e facilitando ataques de IDOR contra `create-checkout`/`create-portal`.
- **Recomendacao:** Remover o parâmetro `userId` controlado pelo cliente; obter o usuário via `supabase.auth.getUser()` no servidor e derivar o `company_id` somente do usuário autenticado (ou validar que o chamador é admin). Não usar a service role para dados que deveriam respeitar o contexto do usuário.

### AUTH-005: CORS permissivo (`Access-Control-Allow-Origin: *`) nas edge functions de faturamento
- **Severidade:** MEDIO
- **Arquivo(s):** supabase/functions/create-portal/index.ts:4-7; supabase/functions/create-checkout/index.ts:4-7
- **Trecho:**
  ```ts
  const corsHeaders = {
    "Access-Control-Allow-Origin": "*",
    "Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type",
  };
  ```
- **Impacto:** Qualquer origem pode invocar as edge functions. Combinado com a autenticação opcional do `create-checkout` (AUTH-002), isso amplia o abuso de criação de sessões de pagamento e leitura/escrita de dados de faturamento a partir de páginas maliciosas.
- **Recomendacao:** Restringir `Access-Control-Allow-Origin` ao(s) domínio(s) da aplicação e manter `Access-Control-Allow-Credentials` desativado, já que a autenticação é feita por header.

### AUTH-006: Enumeração de usuários por mensagens de erro distintas

  if (msg.includes("email not confirmed")) {

### AUTH-007: Política de senha fraca (mínimo de 6 caracteres)
- **Severidade:** BAIXO
- **Arquivo(s):** src/app/login/page.tsx:44-48; src/app/redefinir-senha/page.tsx:26
- **Trecho:**
  ```ts
  if (password.length < 6) {
    notify("Senha inválida", "A senha deve ter no mínimo 6 caracteres.", "warning");
    return;
  }
  ```
  ```ts
  const isStrong = newPassword.length >= 6;
  ```
- **Impacto:** Apenas 6 caracteres são exigidos, sem complexidade, o que facilita ataques de força bruta/credential stuffing contra contas com senhas fracas.

### AUTH-010: Ausência de middleware de proteção de rotas e gate de admin apenas no cliente
- **Severidade:** BAIXO
- **Arquivo(s):** src/app/admin/page.tsx:52-67 (gate client-side); sem `middleware.ts` no projeto
- **Trecho:**
  ```ts
  useEffect(() => {
    async function verifyAccess() {
      const res = await checkAdminAccessAction();
      if (!res.isAdmin) {
        toast.error("Acesso Não Autorizado: Permissão restrita a administradores.");
        router.push("/login?error=unauthorized");
        return;
      }
      setAuthorized(true);
    }
    verifyAccess();
  }, [router]);
  ```
- **Impacto:** Não há `middleware.ts` para bloquear o acesso a rotas autenticadas/administrativas no servidor antes do render. Embora os dados estejam protegidos pelas server actions, a verificação de admin em `/admin` é feita somente no cliente, o que expõe a estrutura da página e depende de JavaScript para redirecionar.
- **Recomendacao:** Implementar um `middleware.ts` com validação de sessão (Supabase SSR) para proteger rotas sensíveis (`/admin`, `/perfil`, etc.) no servidor, mantendo as verificações nas server actions como segunda camada.
