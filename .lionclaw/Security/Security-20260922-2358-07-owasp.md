### OWASP-001: Bucket `simulacoes` público expõe imagens odontológicas de pacientes (dados sensíveis de saúde)
- **Severidade:** ALTO
- **Arquivo(s):** supabase/migrations/20260702000000_storage_buckets_and_rls.sql:8; src/lib/actions/simulacoes.ts:~150; src/lib/simulacoes/actions.ts:~93
- **Trecho:**
  ```sql
  INSERT INTO storage.buckets (id, name, public)
  VALUES 
    ('dentixia', 'dentixia', true),
    ('simulacoes', 'simulacoes', true),
    ('logoEmpresa', 'logoEmpresa', true)
  ```
  ```typescript
  const urlOriginal = supabase.storage.from(STORAGE_BUCKET).getPublicUrl(fileName).data.publicUrl;
  // ...
  const urlSimulada = supabase.storage.from(STORAGE_BUCKET).getPublicUrl(simFileName).data.publicUrl;
  ```
- **Impacto:** O bucket `simulacoes` foi criado com `public = true`. A migration `20260707000000_security_fixes_rls_and_storage.sql` tentou restringir a leitura via RLS, mas **não alterou a flag `public` do bucket**. Em buckets públicos do Supabase Storage, as URLs públicas (`/storage/v1/object/public/...`) são servidas sem autenticação, independentemente das políticas RLS. Como o código gera e persiste `getPublicUrl()` para fotos originais e simuladas de pacientes (dados clínicos sensíveis), qualquer pessoa com o link acessa essas imagens sem login, configurando exposição de dados de saúde e potencial violação à LGPD.
- **Recomendacao:** Tornar o bucket privado (`UPDATE storage.buckets SET public = false WHERE id = 'simulacoes';`) e passar a usar `createSignedUrl()` com validade curta ou um proxy autenticado que valide o proprietário do arquivo antes de servir. Atualizar o código que consome as URLs para o novo modelo de acesso.

### OWASP-002: IDOR em `getProfileCompanyAction` permite obter `company_id` de qualquer usuário
- **Severidade:** MEDIO
- **Arquivo(s):** src/lib/perfil/actions.ts:~18
- **Trecho:**
  ```typescript
  export async function getProfileCompanyAction(userId: string) {
    const admin = getSupabaseAdmin();
    if (!admin) return userId;

    const { data: ucData } = await admin
      .from("user_company")
      .select("company_id")
      .eq("user_id", userId)
      .maybeSingle();

    if (ucData?.company_id) return ucData.company_id;

    const { data: companyData } = await admin
      .from("company")
      .select("id")
      .eq("id", userId)
      .maybeSingle();
    return companyData?.id ?? userId;
  }
  ```
- **Impacto:** A função é uma Server Action (`"use server"`) que recebe `userId` arbitrário do cliente e **não verifica se o `userId` corresponde ao usuário autenticado**. Ela usa o client com `SUPABASE_SERVICE_ROLE_KEY` (bypass de RLS) para consultar `user_company` e `company`. Qualquer usuário autenticado pode invocar a action diretamente e enumerar/descobrir o `company_id` vinculado a qualquer `user_id`, quebrando o isolamento entre tenants e viabilizando ataques de IDOR encadeados.
- **Recomendacao:** Validar a identidade dentro da action usando `const { data: { user } } = await supabase.auth.getUser()` e rejeitar se `userId !== user.id`. Para obter o `company_id` do próprio usuário, remover o parâmetro livre e derivá-lo da sessão autenticada.

### OWASP-003: Open Redirect via `return_url` não validado na Edge Function `create-portal`
- **Severidade:** MEDIO
- **Arquivo(s):** supabase/functions/create-portal/index.ts:~48
- **Trecho:**
  ```typescript
  const { company_id, return_url } = await req.json();
  // ...
  const session = await stripe.billingPortal.sessions.create({
    customer: customerData.stripe_customer_id,
    return_url: return_url || "https://app.dentixia.com/perfil",
  });
  ```
- **Impacto:** O `return_url` é aceito do corpo da requisição sem qualquer validação contra uma allowlist de domínios. Após o usuário sair do portal de faturamento do Stripe, ele pode ser redirecionado para um domínio controlado por atacante, criando um vetor de phishing/open redirect no fluxo de pagamento.
- **Recomendacao:** Validar `return_url` no servidor com uma allowlist estrita (ex.: apenas `https://app.dentixia.com` e subdomínios esperados) ou forçar sempre uma URL fixa/derivada do app, ignorando valores arbitrários do cliente.

### OWASP-004: Enumeração de e-mails cadastrados na resposta de cadastro
- **Severidade:** BAIXO
- **Arquivo(s):** src/lib/auth/actions.ts:~55
- **Trecho:**
  ```typescript
  if (!data.user) {
    return { error: "Este e-mail já está cadastrado. Faça login ou use a opção 'Esqueci minha senha'.", data: null };
  }
  ```
- **Impacto:** O Supabase, com confirmação de e-mail ativa, retorna `data.user = null` silenciosamente para e-mails já cadastrados justamente para evitar enumeração. O código converte esse comportamento em uma mensagem explícita de "e-mail já cadastrado", permitindo que qualquer pessoa verifique se um endereço de e-mail possui conta na plataforma.
- **Recomendacao:** Remover a distinção explícita. Retornar uma mensagem genérica de sucesso (ex.: "Se o e-mail não estiver cadastrado, enviaremos instruções") ou usar o fluxo de verificação por e-mail sem revelar a existência da conta na resposta direta.

### OWASP-005: RLS permite que qualquer usuário autenticado leia todas as notificações do sistema
- **Severidade:** BAIXO
- **Arquivo(s):** supabase/migrations/20260704000000_system_settings_and_notifications.sql:~39
- **Trecho:**
  ```sql
  CREATE POLICY "Authenticated users can read notifications"
  ON public.notifications_history FOR SELECT
  TO authenticated
  USING (true);
  ```
- **Impacto:** A tabela `notifications_history` fica legível integralmente para qualquer usuário autenticado que acesse o banco diretamente (via API Supabase), ignorando a segmentação por `target_audience` feita apenas na Server Action. Notificações destinadas a segmentos específicos (ex.: avisos internos, promoções segmentadas) podem ser lidas por qualquer conta autenticada.
- **Recomendacao:** Restringir a policy de SELECT para considerar o público-alvo da notificação com base no perfil do usuário autenticado, ou expor a leitura somente por meio de uma RPC/função com lógica de autorização e manter a tabela sem leitura direta para `authenticated`.

### OWASP-006: `system_settings` legível publicamente (inclusive anônimos)

  ```sql
  CREATE POLICY "Leitura de configuracoes do sistema"
  ON public.system_settings FOR SELECT
  TO public, authenticated, anon
  USING (true);
  ```
- **Impacto:** Qualquer pessoa, sem autenticação, pode consultar diretamente a tabela `system_settings`. Atualmente expõe ao menos `welcome_video_url`, mas a tabela pode passar a armazenar configurações mais sensíveis, tornando-se uma superfície de vazamento de informações de configuração interna.
- **Recomendacao:** Restringir o `SELECT` a `authenticated` (ou apenas a admins, quando apropriado) e revisar quais chaves realmente precisam ser públicas. Para valores públicos específicos, criar uma RPC dedicada que retorne apenas os campos estritamente necessários.

### OWASP-007: `saveSimulationAction` aceita base64 de imagem sem limite de tamanho ou validação de conteúdo
- **Severidade:** BAIXO
- **Arquivo(s):** src/lib/simulacoes/actions.ts:~5
- **Trecho:**
  ```typescript
  function base64ToBuffer(base64: string): Buffer {
    if (!base64 || typeof base64 !== "string") {
      throw new Error("Formato de imagem base64 inválido ou vazio.");
    }
    const clean = base64.replace(/^data:image\/[a-z]+;base64,/, "");
    return Buffer.from(clean, "base64");
  }
  ```
- **Impacto:** A Server Action não impõe limite de tamanho nem valida o tipo real (magic bytes) da imagem. Um usuário autenticado pode enviar um `base64` arbitrariamente grande, causando alto consumo de memória/CPU no servidor durante a decodificação e upload (potencial DoS), além de gravar conteúdo arbitrário no storage sob o `contentType` forçado.
- **Recomendacao:** Aplicar validação equivalente à de `gerarSimulacaoNativa` (limite de tamanho, ex.: 4 MB) antes da decodificação, validar o MIME real/magic bytes do buffer e rejeitar payloads que não correspondam a imagens JPG/PNG.

### OWASP-008: `salvarSimulacaoConfirmada` persiste URLs fornecidas pelo cliente sem validação de origem
- **Severidade:** BAIXO
- **Arquivo(s):** src/lib/actions/simulacoes.ts:~245
- **Trecho:**
  ```typescript
  const { error: dbError } = await supabase.from("simulacoes").insert({
    usuario_id: user.id,
    procedimento: procedimento,
    img_original_url: urlOriginal,
    img_simulada_url: urlSimulada,
    nome_paciente: nomePaciente.trim(),
    cor_utilizada: corUtilizada,
  });
  ```
- **Impacto:** As URLs `urlOriginal` e `urlSimulada` vêm diretamente do cliente e são persistidas sem verificar se pertencem ao bucket `simulacoes` do próprio usuário. Isso permite gravar URLs externas que serão renderizadas como `<img>` na galeria e no comparador, possibilitando injeção de conteúdo visual de terceiros, rastreamento do usuário (ex.: pixels de imagem) e referências inválidas no histórico.
- **Recomendacao:** Validar que as URLs pertencem ao bucket/domínio esperado do storage e, idealmente, reconstruí-las no servidor a partir de chaves/paths retornados pela geração, em vez de confiar em URLs arbitrárias enviadas pelo cliente.

### OWASP-009: Função `handle_new_user` SECURITY DEFINER sem `SET search_path` explícito
- **Severidade:** BAIXO
- **Arquivo(s):** supabase/migrations/20260706000000_cleanup_and_referral_fix.sql:~54
- **Trecho:**
  ```sql
  CREATE OR REPLACE FUNCTION public.handle_new_user()
  RETURNS trigger AS $$
  -- ...
  $$ LANGUAGE plpgsql SECURITY DEFINER;
  ```
- **Impacto:** A função roda como `SECURITY DEFINER` sem definir um `search_path` seguro. Em cenários onde o atacante consiga criar objetos em schemas anteriores no `search_path` (ou se o `search_path` padrão for manipulável), chamadas a funções/objetos não qualificados dentro do trigger podem ser redirecionadas para objetos maliciosos, caracterizando o ataque de "function search_path hijacking". O risco é baixo no ambiente atual, mas é uma falha de hardening relevante para funções privilegiadas.
- **Recomendacao:** Adicionar `SET search_path = pg_catalog, public` (ou um schema controlado) à função e qualificar explicitamente todos os objetos referenciados, à semelhança do que já foi feito em `public.is_admin()`.

### OWASP-010: CORS permissivo (`*`) na Edge Function `create-portal`
- **Severidade:** BAIXO
- **Arquivo(s):** supabase/functions/create-portal/index.ts:~4
- **Trecho:**
  ```typescript
  const corsHeaders = {
    "Access-Control-Allow-Origin": "*",
    "Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type",
  };
  ```
- **Impacto:** A Edge Function aceita requisições de qualquer origem e permite leitura da resposta por qualquer site. Embora a autenticação por token ainda seja exigida, essa configuração amplia o impacto de eventual roubo/uso indevido de token e não restringe o consumo da API aos domínios oficiais do produto.
- **Recomendacao:** Restringir `Access-Control-Allow-Origin` aos domínios confiáveis do app (ex.: `https://app.dentixia.com`) e manter uma lista explícita, em vez de usar `*`.
